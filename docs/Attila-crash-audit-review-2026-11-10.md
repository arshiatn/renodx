## Problems in the fixed tree, most severe first

### Unload-time fence recovery creates a D3D12 device inside AddonUninit: ReShade re-enters its add-on manager and frees the addon DLL under its own running code

- Where: `src/games/twattila/dlaa_bridge.hpp:383` (review unit F1-lifetime)
- Severity: reviewer high, verifier high; verifier's verdict: confirmed
- Scenario: State: DLAA/RT/FG running, the helper hangs or dies with a request outstanding, and the game destroys its device (GPU-error recovery, fullscreen change, or quit) before the fence completes. ~D3D11Device -> reshade::unload_addons() (s_reference_count now 0) -> AddonUninit -> Shutdown: 5 s fence wait expires -> StopSession kills the helper -> line 463 Rescue(pending.value, fence) -> line 383 pD3D12CreateDevice. That pointer is GetProcAddress(system d3d12.dll) which ReShade detours (dll_main.cpp:348). ReShade's hook (source/d3d12/d3d12.cpp:40) calls load_addons(): count 0->1, so it runs the full load: calls AddonInit on our still-registered module (addon_manager.cpp:205) -> AttachAddon re-registers every event and hook and restarts the startup worker, while the outer AddonUninit is still on the stack. When recovery_device is released at Rescue's return (or immediately at d3d12.cpp:62 if device creation fails, likely in the 32-bit games) the count returns to 0 -> nested unload_addons -> nested AddonUninit (DetachAddon + Shutdown re-entered while the outer StopSession is iterating bridge.retired_fences and holds rescue_mutex) -> FreeLibrary(addon) drops the only reference and unmaps the DLL. Control then returns into the unmapped outer frames (Rescue/StopSession/Shutdown): access violation in the game. Result: a crash exactly in the 'helper stalled + device recreated' case the fix was written for. test/tw_helper_lifetime passes because no ReShade is loaded there.
- Suggested fix: Do not create any device (D3D11 or D3D12; both create functions are ReShade-hooked and call load_addons) from AddonUninit. In Shutdown skip Rescue and only log: the game's device proxy is already being destroyed, so its queued wait no longer drives a picture. If recovery must stay, do it with a device made earlier while the add-on reference count is above zero (for example a recovery device kept from Start), never one created during unload.
- Verifier: Traced end to end in the fixed tree and the vendored ReShade source (external/reshade/source); I found no guard.

1. addon.cpp:2016-2018: AddonUninit runs DetachAddon, then dlaa_bridge::Shutdown, and only then unregister_addon. So the add-on is still in addon_loaded_info during Shutdown.
2. dlaa_bridge.hpp:1414-1433: Shutdown waits 5 s on the retired fences, then StopSession terminates the helper. Lines 458-463 call Rescue(pending.value, fence) for every incomplete fence. Release() (anti_aliasing destroy_device, line 1641) and RetireFence keep an incomplete fence in retired_fences, so the path is reachable.
3. Rescue line 383 calls pD3D12CreateDevice, which is GetProcAddress(d3d12.dll) (utils/directx.hpp:95-104). ReShade registers system d3d12.dll for hooks (dll_main.cpp:348) and installs them on LoadLibrary (hook_manager.cpp:312+), so the call lands in ReShade's D3D12CreateDevice.
4. d3d12.cpp:40 calls load_addons(). AddonUninit is called from unload_addons only after s_reference_count reached 0 (addon_manager.cpp:337), so this is 0->1 and a full load. Lines 193-205 call AddonInit on every still-registered module. Ours has addon_registered true and attached false, so AttachAddon re-registers all events and hooks and restarts the at-start thread.
5. The D3D12Device proxy takes a reference (d3d12_device.cpp:37) and d3d12.cpp:87 drops the temporary one. recovery_device is declared inside the if block, so it is released at Rescue's return while the rescue_mutex lock (declared first) is still held. ~D3D12Device calls unload_addons, 1->0, giving a nested AddonUninit, and then FreeLibrary(module) at addon_manager.cpp:362 because info.external is false for an add-on ReShade loaded itself.
6. I found no extra module reference: the only GetModuleHandleEx in the addon uses UNCHANGED_REFCOUNT. So the DLL is unmapped while the outer Rescue, StopSession, Shutdown and AddonUninit frames are still on the stack.

Even before the unmap, the nested Shutdown runs erase_if and clear on bridge.retired_fences while the outer range-for is iterating it. If the fence was not recovered, the nested Rescue re-locks the non-recursive rescue_mutex on the same thread. On the failure branch (d3d12.cpp:62) the same 1->0 unload happens inside the CreateDevice call.

Two things I could not establish from code: whether the installed ReShade build matches the vendored source (this load/unload counting is long-standing), and whether g_in_dxgi_runtime is set on the destroying thread (it is only set around specific create and present calls). The trigger is narrow: the helper must be stalled or dead with a fence incomplete for more than 5 s, and the game must destroy its D3D11 device. When it happens the result is a crash or hang in the game, and it is new with this fix: the pre-fix AddonUninit did not call Shutdown or Rescue. High stands.

### After a GPU reset the helper now kills itself and F7 makes that permanent (F9 + F7 interaction)

- Where: `src/games/twattila/dlaa_helper/gpu_completion.hpp:32` (review unit F7-watchdog)
- Severity: reviewer high, verifier high; verifier's verdict: confirmed
- Scenario: A GPU reset (TDR) removes the helper's D3D12 devices, which is the reported symptom (frozen picture, HDR dropped). Pre-fix the helper survived: main.cpp 527-531, 576 and 666-669 build new devices ('A GPU reset removed ... device: a new one'). In the fixed tree, WaitForGpu returns false when the fence reads UINT64_MAX (removed device), and RequireGpuCompletion then calls StopGpuProcess. Replacing a lost object runs its destructor, e.g. ~RayReconstruction12 at rr_d3d12.hpp:232 calls WaitFor(own_value_), so the helper terminates itself on the very path meant to recover. The bridge watcher sees the exit (dlaa_bridge.hpp:555-557) and sets watchdog.failed, which nothing but Shutdown clears. Result: after any GPU reset DLSS/RR/RT/FG are off until the game restarts, where before they came back. Traced by reading only; not run.
- Suggested fix: In WaitForGpu treat a removed device (UINT64_MAX) as 'nothing left to wait for' and return to the existing device-rebuild code instead of terminating; or let the bridge restart the helper once after an exit (StopSession, then Start) instead of latching watchdog.failed for the session.
- Verifier: Traced in the fixed tree, not run. gpu_completion.hpp:31-32 and 38 return false when the fence reads UINT64_MAX, before the `completed >= value` test, so even a wait for value 0 fails; RequireGpuCompletion (48-50) then calls StopGpuProcess (TerminateProcess). rr_d3d12.hpp WaitFor (line 254) uses it and is called from ~RayReconstruction12, Close, ReleaseFeature and Record. Pre-fix WaitFor was `if (GetCompletedValue() >= value) return;`, so a removed device passed straight through and main.cpp 527-531 / 532-536 / 576 / 666-669 / 374-383 rebuilt the object. Those recovery lines are still there but are now unreachable in practice: `reconstruction = std::make_unique<...>()` at main.cpp:529 runs the old destructor, which hits WaitFor on the removed device's own fence and terminates. It is wider than the reviewer states: every queue Wait/Signal is now wrapped in RequireGpuResult (rr 206/211/212, rt 1132-1138 and 1597-1603, upscale 328-334, fg 499-505 and 615-629), which also terminates on DXGI_ERROR_DEVICE_REMOVED, and Evaluate's Record calls WaitFor first, so the helper dies on the first request after removal even before main.cpp's Lost() checks. The harness switch RENODX_TW_TEST_DEVICE_REMOVAL (rr_d3d12.hpp Evaluate, comment 'main.cpp makes a new one') would now end the process too. Bridge side: watcher sets watchdog.failed on exit (dlaa_bridge.hpp:555-557); the only reset is Shutdown (1450), called only from AddonUninit; Start returns !bridge.failed (489) and is never re-run. So DLSS/RR/RT/FG stay off until the game restarts. No guard found. The audit doc line 518 says this is deliberate ('replaces in-process recovery ... with helper exit'), so it is a chosen trade-off, but the regression against the pre-fix recovery is real and hits exactly the reported symptom (GPU reset). The only assumption not provable from code is that a removed D3D12 device's own fence reads UINT64_MAX, which is documented D3D12 behaviour and the repo's own comments rely on it.

### Tales of Arise: the shared RR header now terminates the GAME process

- Where: `src/games/twattila/dlaa_helper/gpu_completion.hpp:18` (review unit F9F10-helper-wait)
- Severity: reviewer critical, verifier high; verifier's verdict: confirmed
- Scenario: src/games/talesofarise_dlss/rr_d3d12.hpp:18 includes twattila/dlaa_helper/rr_d3d12.hpp and runs RayReconstruction12 inside Tales of Arise.exe (talesofarise_dlss/addon.cpp:48, member `gpu_->reconstruction`). The fix did not touch talesofarise_dlss. StopGpuProcess is TerminateProcess(GetCurrentProcess()), so in Tales any of: the add-on's D3D12 device removed (GPU reset), an own-fence wait over 5 s (rr_d3d12.hpp:254 via Record:260/269, Close:181, ReleaseFeature:220, destructor:232), a failed queue Wait/Signal (rr_d3d12.hpp:206-212), or CreateEvent failing (133) kills the game instantly: no crash dialog, no dump, no log line, unsaved progress lost. Before: Record returned Fail('Ray Reconstruction: D3D12 stopped'), Evaluate returned false and the addon ran Super Resolution instead. The header comment 'the bridge recovers its fences only after observing helper process exit' is false for this consumer.
- Suggested fix: Do not put process termination in a header shared with in-process users. Make WaitFor return bool and let each owner decide (helper: fail the backend / replace the object; Tales: Fail() and fall back to Super Resolution), or at least compile the kill only in the helper exe.
- Verifier: Traced. talesofarise_dlss/rr_d3d12.hpp:18 includes twattila/dlaa_helper/rr_d3d12.hpp and holds `twattila::dlaa_helper::RayReconstruction12 reconstruction` in its Gpu struct (line 179), initialised on the add-on's own in-process D3D12 device (line 77) and evaluated at line 139 from addon.cpp:1258. `git diff 0a6cd493..origin/atn-mods -- src/games/talesofarise_dlss` is empty, so the consumer was not adapted. gpu_completion.hpp:16-20 StopGpuProcess = TerminateProcess(GetCurrentProcess()) with no check of which process it is in. Reachable in the game process via Record -> WaitFor(slot->value) (rr_d3d12.hpp:260 -> 254), Close (181, called from Open 159), ReleaseFeature (220, addon.cpp:1261), the destructor (232), queue Wait/Signal (206/211/212) and CreateEvent (133). Pre-fix WaitFor returned after at most 5 s and Record returned Fail('D3D12 stopped'), so Tales fell back to Super Resolution (rr_d3d12.hpp:156 `if (!evaluated) return false`). No guard found. Severity lowered from critical to high: it needs Tales' Ray Reconstruction (Experimental) on plus a device removal or a >5 s stall of the add-on's queue, and a removal of the add-on's D3D12 device often comes with the game's own D3D11 device being lost. Still a silent kill of the game with no dump or log line where there used to be a graceful fallback.

- Scenario: One of the helper's D3D12 devices is removed (TDR 0x887A0006/7, or the harness's RENODX_TW_TEST_DEVICE_REMOVAL at rr_d3d12.hpp:199). - Verifier: Traced. A removed D3D12 device makes ID3D12Fence::GetCompletedValue return UINT64_MAX (documented; the repo relies on it too). gpu_completion.hpp:32 returns false for that before the `completed >= value` test, and RequireGpuCompletion (49) terminates. Every recovery path in main.cpp destroys or closes the lost object and so hits such a wait: 527-529 `reconstruction = make_unique` -> ~RayReconstruction12 (rr_d3d12.hpp:232 WaitFor(own_value_)); 532-534 -> ~Upscaler12 (upscale_d3d12.hpp:347); replace_lost_scene 315 -> ~RtScene12 (rt_d3d12.hpp:1615); open_generation 376 generation->Shutdown -> FreeResources -> WaitIdle (fg_d3d12.hpp:623-630, Signal on a removed queue fails -> RequireGpuResult kills, else WaitFor kills); 413 -> ~ProxyFrameGeneration12 -> FreeResources -> WaitIdle. Pre-fix (0a6cd493) each WaitFor was `if (GetCompletedValue() >= value) return;`, which returns at once on all ones, so the 'a new one' recovery ran. These checks run at the top of every request (main.cpp:522-536), so the first request after a removal kills the helper; the recovery code is unreachable. Addon side: the watcher sets watchdog.failed on helper exit (dlaa_bridge.hpp:555-557), Request/Prepare return Fail (701, 953, 999), Fail sets bridge.failed (334), Start returns `!bridge.failed` once started (489), and started/failed are reset only in Shutdown (1448-1450), which is called only from AddonUninit (twattila/addon.cpp:2018). So nothing restarts the helper within the session. The harness hook RENODX_TW_TEST_DEVICE_REMOVAL (rr_d3d12.hpp:199-200) would now end the helper instead of exercising recovery. One caveat I could not establish from code: how often on a real TDR only a helper device is removed while the game's D3D11 device survives. The main.cpp comments (663-665, 490-491 '0x887A0007: reset, another's work') say this happened and was recovered.

### New permanent off: a helper GPU stall over 5 s (or the helper's own F9 exit) ends DLSS/RR/FG/RT until the game restarts

- Where: `src/games/twattila/dlaa_bridge.hpp:572` (review unit fresh-eyes-bridge)
- Severity: reviewer medium, verifier high for the GPU-reset part (understated); the 5 s stall part stays plausible / medium; verifier's verdict: confirmed

- Suggested fix: Allow one bounded helper restart after a watchdog kill or helper exit (reset started/failed/watchdog.failed once the old process is confirmed gone and its fences recovered), and treat a fence at UINT64_MAX as the self-healing reset path rather than a fatal one.
- Verifier: Addon side, confirmed: the watcher (dlaa_bridge.hpp:552-592) sets watchdog.failed on helper exit or when a watched fence makes no progress for its timeout. The timeout is 5 s for steady requests and 5 s after each CPU answer (line 646). It then terminates the helper. Nothing restarts it: `started` stays true and watchdog.failed is cleared only in Shutdown.

Helper side is worse than the reviewer says. gpu_completion.hpp WaitForGpu returns false whenever the fence reads UINT64_MAX (checked before `completed >= value`), and RequireGpuCompletion then calls StopGpuProcess (TerminateProcess on itself). The destructors call it: ~RtScene12 (rt_d3d12.hpp:1615), ~RayReconstruction12 (rr_d3d12.hpp:232) and ~Upscaler12 (upscale_d3d12.hpp:347) all run `WaitFor(own_value_)`. The helper's own recovery after a GPU reset is to destroy the lost object and make a new one: main.cpp:315 (`scene = make_unique` in replace_lost_scene), :529 (reconstruction), :534 (upscaler). A removed D3D12 device leaves its fence at UINT64_MAX, so each of those recoveries now kills the helper. RequireGpuResult on queue Signal/Wait (e.g. rt_d3d12.hpp:1132-1138) does the same when the device is removed mid-request.

So a GPU reset that used to self-heal ('Started again on a new device', main.cpp:327-331) now ends in helper exit, then watchdog.failed, then everything off until the game restarts, plus the per-frame log lines of the previous finding. This follows from code plus documented D3D12 behaviour; it was not run.

Whether healthy play ever goes 5 s without fence progress (heavy BLAS or cluster builds on the worker) cannot be established from code.

Nits: (1) a colour-space failure is now fatal for DLSS-G for the whole session where it used to be ignored (see problems); (2) the same-size switch calls SetColorSpace1 while generation is on, without the SetGeneration(0) / presents_after_resize_ sequencing the resize path uses - not verified against Streamline, needs a hardware HDR->SDR->HDR test. ### F12

- Original (partly): Pre-fix: each preset change did std::thread(...).detach() and SavePreset serialised with a static mutex (0a6cd493 fg_d3d12.hpp ~377, ~663). Mutex acquisition order is not FIFO, so with one save in flight and two more waiting, the older could run last and persist a stale preset; preset_result_ was shared by all. Real, but it needs three preset changes inside one NVAPI save (or an unlucky thread start), only affects which preset the driver profile holds at the next game start, and has nothing to do with the freeze/crash. P3 rather than P2.
- Fix (correct-with-nits): PresetWriter is correct: one owned worker, state under one mutex, predicate wait (no lost wakeups: Request changes requested_ and notifies while holding the mutex; the worker re-checks completed_ != requested_ after every save), coalescing to the latest preset, result published only for the current generation, thread-creation failure handled and retried on the next Request. Destructor sets stopping_, the worker still drains a pending request, then exits; join is safe. Member order is fine (preset_writer_ is destroyed after chain/window). No lock-order issue: the worker calls save() unlocked. Hot path: nothing per frame; Result() takes a shared lock every 30 presents. Player-visible change when nothing fails: status line briefly shows "(saving preset)". Nit: the destructor join now blocks the helper's main thread for the rest of an in-flight NVAPI save (see problems). The test is honest (fake save, checks 1/3/4 order and drain) but only tests the new class, not the old two-thread race.

### F13

- Original (real): Pre-fix DrawHudless (0a6cd493 frame_generation.hpp:276-301): `objects = {.device = device1}` before creation and again in the failure branch, then return false. Next call on the same device skips setup (device matches) and goes on to UpdateSubresource(objects.injection == null), SwapDeviceContextState(null) and draws with null shaders; OnReshadePresent's scRGB path used context_state / hdr10_pixel_shader with only a size check. Most likely trigger is a device already being removed, i.e. a consequence of the freeze, not its cause.

### F14

- Original (partly): The code path is real, but the trigger is close to unreachable and it does not match the reported crash. Pre-fix (0a6cd493) graphics_hooks.hpp:531-539 and twrome2/engine_tweaks.hpp:646-654 catch any exception from detour::Uninstall, comment it as 'the game is closing', and clear the hook records unconditionally. DetachAddon runs from AddonUninit (twattila/addon.cpp:2016), which ReShade calls on a live unload, so a failed detach would leave game code jumping into an unmapped DLL. However, a failure needs DetourTransactionBegin, DetourDetach or Commit to fail (src/utils/detour.hpp:97-165). Each addon links its own Detours copy, and the only Detours users in the three 32-bit TW addons are these two hook sets, removed one after the other on one thread. I found no realistic way for the transaction to fail. P1 is overstated; it is a hardening item. A frozen picture, HDR drop and white scene is not an addon-unload symptom, and nothing here explains it.
- Fix (correct-with-nits): The fix is sound for what it targets; I found no new bug on the normal path.

- **Refcount balance:** correct. Install pins once via GetModuleHandleExW (native_hook_lifetime.hpp:31-35, no UNCHANGED_REFCOUNT, so +1). It releases on install failure (:38-41) and on successful removal (:56-58). Reinstall after a clean removal pins again because module was reset to null. The two owners (graphics hooks, LOD pick) each hold and release their own reference.
- **Normal removal:** the pin is released inside Uninstall before ReShade's FreeLibrary, so the DLL unmaps exactly as before. No second copy and no stale statics on a normal reload.
- **After a failed removal:** the DLL stays mapped. ReShade's next LoadLibrary returns the same image without DllMain; AddonInit re-registers because AddonUninit cleared addon_registered. Trampolines and original_* pointers live in or are referenced from that same image, so reuse (graphics_hooks.hpp:478-482, engine_tweaks.hpp:357-360) is valid.
- **Discovery flags:** resetting graphics_found and graphics_hooks_installed in AttachAddon is needed for that reuse and is a no-op on a fresh load. LOD pick is re-armed through engine_tweaks::Update because graphics_found is reset.
- **Between 'disabled' and detach:** hooks pass straight through to the original; safe.
- **Hot-path cost:** one relaxed atomic load per hook call and one vector-empty check per present; negligible. No visible change when nothing fails.
- **Include direction:** twattila/graphics_hooks.hpp already included ../twrome2/engine_tweaks.hpp before the fix, so placing the new header in twrome2 follows the existing layering.

Nits and gaps:
- A thread already inside a hook body when a successful detach and unload happens can still return into unmapped code. This existed before the fix, is unchanged, and Astra's notes admit it.
- The reuse path returns before the 'status->label +=' line, so the overlay status loses the hook result after a retained reload. Cosmetic.
- The same swallow-and-clear pattern remains at four Shogun 2 DLSS sites (see problems).
- The test exercises Lifetime and the real callbacks but builds the hook list by hand; it does not run the production install path in Update(). The 'commit failure' stage is a simulated abort, as disclosed.

### F15

- Original (real): Real, but low impact. Pre-fix depth_levels.hpp:91-97 writes depth_width/height before allocating. On failure (:127-134) it resets only texture and view, so every later Build at that size skips allocation and returns nullptr until the size or device changes. level_writes and level_views were not cleared, so partial views kept the texture alive. The consequence is only a lost optimisation: callers bind null at t41 and the shader falls back to depth-only (depth_levels.hlsli: count 0 means none bound). It is not a crash path and is unrelated to the reported freeze.
- Fix (correct-with-nits): The fix is correct and I found no behaviour change on the success path.

- **Cache key:** dimensions are published only after the texture, aggregate SRV and all five UAV/SRV pairs exist (depth_levels.hpp:141-144). Failure clears every reference (:134-137).
- **Clock cost:** steady_clock::now() at :95 sits inside the rebuild branch only. The cached same-size path never touches the clock. It costs one QPC read per rebuild, or per AO pass while a failure is pending.
- **Alternating sizes:** the fix does not change this. It is still a single-entry cache that rebuilds on any size mismatch, exactly as before. The cooldown blocks all sizes for up to 1 s only after a real allocation failure, and during that time callers get the depth-only fallback.
- **Callers:** ao_pass.hpp:241 makes one Build per AO draw. line_sweep_ao.hpp:95 calls it from OnBlur and OnCollect, and Warhammer III has two collect sites. I did not prove whether any game passes two depth sizes in one frame; if one does, it was already rebuilding every call before the fix.
- **Null handling:** both callers bind the null view at slot 41 (ao_pass.hpp:241-242, line_sweep_ao.hpp:95-97) and the shader handles it.
- **Locks:** order is unchanged (ao_pass mutex, then depth_levels mutex). ao_pass::Update and OnDestroyDevice reset the whole struct, which also clears retry_after.
- **Test:** it compiles the production header with the three create calls redirected and checks rollback, cooldown and same-size recovery at all 12 steps. It tests what it claims.

Nit: a permanent failure now retries and logs once per second for the rest of the session instead of once (see problems).
